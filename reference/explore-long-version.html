The short version

One idea: the operation lives in a database, not in a chat

Today the website is a calculator that ends in WhatsApp. Everything after that (data, proof of payment, verification, bookkeeping) happens in chat and by hand. The whiteboard moves that work into a structured flow; Kambista shows how a client-facing version of it can feel.

whiteboard

Web App → BD → VIEW → Dashboard → Script

Client data and voucher photos land in a database; a person validates each payment through a VIEW (about 15 min) and marks orders to export; the existing Dashboard imports and exports orders; a script registers the sales through the providers’ APIs.

3 · To-be

The whiteboard flow, redrawn

Everything below the red line on the board, drawn with its actors: who does each step and in which system. Three rules shape it. Payment validation stays with a person who works in the VIEW. The Dashboard is the existing system and is not modified: it only imports and exports orders. And AI appears only where similar remittance and exchange businesses already use it, as optional pieces.

Optional evolutions

Three AI pieces already used by similar businesses, and one experimental

I kept only the pieces for which I found a real deployment in remittance or currency-exchange companies, and each now sits in the graph as an actor that exchanges data with the flow. A1 to A3 meet that test. A4, for the Fact script, does not: I found no deployment, and the table says so. None of them approves a payment or edits fiscal data. The base flow runs with all of them switched off. Most sources are company, partner or vendor write-ups, so the performance claims are unaudited.

Ground rules
  • AI never approves a payment and never changes a money value.
  • Each piece has a feature flag; the base flow keeps working with all of them off.
  • Store the input reference, model or vendor and the answer in events for audit.
  • Voucher and ID images are personal data: private storage, a provider with data controls, redacted logs.
Where I would start suggested
  • A1 on Telegram first (no approval needed), WhatsApp when the Business Platform is ready.
  • A3 as plain rules first, so the VIEW already has the column; swap in a vendor score later.
  • A2 only if a vendor covers DNI and CPF at an acceptable cost.
  • A4 last, and only after the rule-based checks in Fact work and real rejections show it is needed.

Guardrails and handoff

The agent must never…
  • say a payment is received or approved; it only repeats the status the validator set in the VIEW
  • treat the voucher image as proof: the validator checks it against the bank
  • write a rate, fee or account number itself; those come verbatim from tools
  • invent a rate when the rates service is down: it says so and hands off
  • give financial or legal advice
Hand off to a person when…
  • the client asks for one, or writes a complaint or claim
  • the client reports a problem with the voucher, the amount or the account
  • the rate lock expired mid-flow, or the amount is above a limit limit to define
  • a first-time client needs identity checks process to define

9 · Billing script

The flow behind “Script Fact”

Fact takes a set of orders that a person exports from the Dashboard and imports into Fact, which then runs the whole set. It registers each sale through the provider’s API with the tax authority (SUNAT in Peru through KeyFácil, the Brazilian equivalent through Omni), builds the PDF itself from the XML it gets back, and emails that PDF. It replaces today’s billing steps 6 to 9: pre-validate, register in KeyFácil / Omni, consolidate, email.

one exported file, many records; each record succeeds or fails on its own
XML is the document
the tax authority’s XML is the legal source; it is stored untouched
PDF is derived
generated from the stored XML, so it always shows what was registered

Why the PDF comes from the XML

  • Peru: the signed XML (UBL) is what SUNAT receives. The printed representation must show a QR code and the hash (the XML’s DigestValue), with the minimum content set by SUNAT resolutions (see Res. 340-2017). I did not verify the exact field list.
  • Brazil: the authorized XML is the only fiscal document; the PDF (DANFSe for the national NFS-e) has no fiscal validity and its QR points to the public consultation (overview). One blog reported the national PDF-generation service offline in August 2026, which is a reason to render it ourselves; open-source renderers exist (example).
  • Test environments: run against the providers’ test (homologación) mode first; Brazilian test PDFs carry a “no legal validity” mark.
to verify Which document Omni emits in Brazil (NFS-e national, municipal or NF-e), and whether KeyFácil / Omni return the signed XML in the API response. The PDF step depends on that.

Pseudocode of the job

# input: the set of orders a person exported from the Dashboard and imported into Fact
batch = ingest(file)                                   # 1 schema + checksum, skip already-invoiced ids
for rec in batch.records:                              #   bounded concurrency
    try:
        check(rec)                                     # 1 country rules; DataError → rechazado_validacion
        svc = service_for(rec.direction)               # 2 PE→BR: keyfacil → SUNAT · BR→PE: omni → BR authority
        res = svc.register_sale(rec, key=rec.operation_id)   # idempotent; returns xml (+ cdr / protocol)
        if res.rejected:  mark(rec, "error_fiscal", res.code); continue
        if res.pending:   mark(rec, "pendiente_autoridad");   continue   # polled later
        store_xml(rec, res.xml, res.cdr)               # 3 untouched, hashed
        pdf = render_pdf(res.xml)                      # 4 from the XML, never from the DB
        assert totals(pdf) == totals(res.xml)          #   PDF ≠ XML → error_pdf, no email
        send_mail(rec.customer.email, pdf)             # 5 log message id
        mark(rec, "facturada")
    except DataError  as e: mark(rec, "rechazado_validacion", e)
    except Transient  as e: retry_later(rec, status_check=True)  # ask the service before resending
report(batch)                                          # 6 per-row result to the BD / VIEW + daily consolidated
Rules that keep it safe
  • Idempotent: the operation ID is the key; re-running a batch continues the unfinished records and never duplicates a sale.
  • XML is immutable: store it with its hash; the PDF can always be rebuilt from it.
  • Secrets: API keys in a server-side secret store, never in the web bundle, rotated (the board’s “API Key !!”).
  • Private storage for XML and PDF; links to customers are signed and expire.
  • Audit trail: every call and the raw answer in events.
  • Test mode first on both services before real sales.
Timing against the 20-minute target
  • The script is fast when the services answer: seconds per record, minutes per batch.
  • What decides the target is how soon operators export and confirm. Small, frequent batches (for example every 15 min or on each confirmation) beat one daily batch.
  • If an authority answers asynchronously, the receipt waits for it; the client is told the status meanwhile.
