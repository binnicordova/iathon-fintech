The idea in one minute

One change: every operation gets a record

Right now the website ends in WhatsApp and everything after that is done by hand. The new flow keeps WhatsApp as a help channel, but saves each operation in one place so people can check it, bill it and follow it.

Today

Chat and spreadsheets

Clients quote on the website, then data, proof of payment and checks all happen in WhatsApp. Staff retype each order into the Dashboard and again into the invoicing tools.

New flow

Web App or chat → database → VIEW → Fact

The client enters data in a Web App, or chats with an AI assistant on WhatsApp or inside the app. A person checks the bank and approves in a VIEW. The Dashboard is not changed. A script (Fact) registers the sale and emails the PDF.

1 · Today

How an operation works now

1 · QuoteThe client uses the calculator on brasper.com and taps “Enviar por WhatsApp”.
→
2 · ChatA sales agent agrees the rate and collects the data in WhatsApp.
→
3 · ProofThe client pays and sends a screenshot of the transfer.
→
4 · Check and typeThe agent looks at the screenshot and types the operation into the Dashboard.
→
5 · BillingBilling re-checks it, then registers the sale in KeyFácil (Peru→Brazil) or Omni (Brazil→Peru).
→
6 · ReceiptThe receipt is emailed to the client, up to 3 days later.

What gets in the way

  • Nothing is saved by the website. Its only result is a WhatsApp message.
  • Proof of payment is a screenshot checked by eye, with no record of who decided. That is a fraud risk.
  • The same data is typed twice (Dashboard, then KeyFácil or Omni), which causes mistakes.
  • There is no defined data structure. The board flags it in red: “dB Schema!!!”.
  • Waiting. WhatsApp queues, and the receipt can take up to 3 days.
Fix on the live website first: (a) the calculator could not load rates on 10 Oct, so it shows 0; check from another network; (b) an expired promotion (“until 9 April”) is still shown, and “3 steps” lists four; (c) a secret value is visible in the site’s public code and should be changed.
2 · Learning from a similar app

What Kambista does that we can borrow

Kambista is a Peruvian exchange app. I walked through an exchange on a real phone: everything happens inside the app, in three steps. Full walkthrough.

  • Ask for the same three things: bank, destination account and source of funds.
  • Show where to pay, with copy buttons and a reminder to use the right currency account.
  • Ask for the operation number and proof, then show a status timeline.
  • Keep saved accounts so returning clients do not retype them.
3 · The new flow

Who does what, and in which system

The whiteboard flow, drawn with its actors. Blue boxes are what we build, purple boxes are the AI chat assistant, the grey box is the Dashboard that stays as it is, and the dashed purple piece is optional AI (use the switch to hide it).

#WhoWhat happens
1ClientQuotes with the current exchange rate, in one of three ways: the Web App form, a WhatsApp chat, or the assistant inside the Web App. See What people see.
2ClientGives the source of funds, source account, operation number and destination account, pays, and sends the proof photo, by form or by chat. All three ways save the same data in the database, one record per sale (“IV”, Intención de Venta).
3ValidatorSees the pending operations in the VIEW, checks the bank (target about 15 minutes) and approves.
4OperatorMarks the approved operations in the VIEW and exports a file of orders.
5OperatorImports that file into the Dashboard. The Dashboard is not changed: it only imports and exports orders.
6Billing personExports the orders from the Dashboard and imports the file into Fact, which runs the whole set.
7FactRegisters each sale with the tax authority (SUNAT through KeyFácil, the Brazilian equivalent through Omni) and keeps the official XML. See Billing.
8FactBuilds the PDF from that XML and emails it to the client. The result goes back to the database and shows in the VIEW.

The validator, the operator and the billing person may be the same people; the team should confirm (see Questions).

5 · Billing script (Fact)

From imported orders to a PDF in the client’s inbox

A person imports a set of orders into Fact. For each order, Fact registers the sale with the tax authority, saves the official XML it gets back, builds the PDF from that XML and emails it. This replaces today’s manual billing steps: re-check, register, consolidate, email.

#StepIn plain words
1Check the batchFact reads the file and checks each order: ID number format, email, amounts that add up, not already invoiced. A bad order is set aside and the rest continue. Importing the same file twice is safe.
2Register the saleFor each order Fact asks the invoicing service to register it: KeyFácil for Peru→Brazil (which reports to SUNAT) and Omni for Brazil→Peru (which reports to the Brazilian tax authority). The answer is accepted or rejected, and the service sends back an XML, the official electronic record.
3Save the XMLStored exactly as received and never edited.
4Create the PDFBuilt from that XML, so it always shows what was registered. Fact compares the totals before saving it.
5SendEmailed to the client only after the tax authority has accepted the sale.
6ReportThe result of every order (invoice number or error) is saved and shown in the VIEW, and the daily consolidated file is produced. The Dashboard is not involved.

If something goes wrong

CaseWhat happens
The order data is invalidIt is set aside and listed in the report. A person fixes it at the source (VIEW or database) and exports it again.
The tax authority rejects itIt is marked with the reason, with no automatic retry. A person corrects the data and resubmits.
The service is down or slowFact retries. Before resending it asks the service whether the first attempt went through, so a sale is never registered twice.
The email bouncesThe team is alerted and the PDF stays available in the VIEW.
Why the PDF comes from the XML
  • Peru: the signed XML is what SUNAT receives. The printed version must show a QR code and a hash, with the minimum content set by SUNAT (Res. 340-2017; I did not verify the exact field list).
  • Brazil: the authorized XML is the only fiscal document. The PDF (DANFSe) has no fiscal validity (overview).
What each order must carry

Operation ID, direction (PE→BR or BR→PE), document type, the client’s ID type and number (DNI, RUC, CE, passport, CPF or CNPJ), name, email, a description and amount, and the tax code. The accountant defines which amount is billed and every tax field; Fact checks and sends them, it does not decide tax treatment.

Checks are plain rules; AI comes after, and only as the optional A2. Run everything on the services’ test mode first. On the rule that the PDF goes out only after acceptance, a Sovos summary says SUNAT advises against delivering a receipt before validation (Sovos Peru); confirm it with the accountant.
6 · AI in the flow

The chat assistant, and one optional extra

The chat assistant is part of the core flow. The rejection explainer is optional and experimental. I kept only AI that similar companies already use, and a person always decides: AI never approves a payment or changes tax data. Most sources are company write-ups, so their claims are unaudited.

What it doesSeen in similar companiesLimits
A1Chat assistant (core). Talks with the client on WhatsApp and inside the Web App, asks one question at a time, fills in the same data as the form, collects the proof photo and operation number, answers “where is my order?”, and hands over to a person when asked or when unsure.Félix Pago sends remittances through a WhatsApp chatbot (Stripe case study). Rextie, a Peruvian exchange house, has a chatbot, “Lucía” (Andina, undated).Automating WhatsApp needs the official WhatsApp business service; the site only opens a plain chat link today. Rates, fees and account numbers always come from the system, never from the assistant’s own words.
A2Rejection explainer (in Fact, optional). Says in plain words why the tax authority rejected an order and what to check.None found: experimental. The problem is real: some Brazilian rejections are generic, for example code E8214 (Omie help).Build it only if real rejections show it is needed. It never edits tax data.

Left out because I found no similar company using them: reading voucher photos automatically, a triage assistant for exceptions, asking the database questions in plain language, and a custom fraud model.

7 · First release

What we can ship in four days

The normal path only: an operation from quote to PDF receipt. Special cases and AI come later.

In the MVP
  • Web App: quote, data, pay, upload proof, status.
  • A database that keeps everything: clients and accounts, quotes, operations, proof photos, who validated and when, billing batches and invoices.
  • The chat assistant: on WhatsApp and inside the Web App, for quote, data, proof and status, saving the same data as the form. Until the official WhatsApp account is ready, use a test number or Telegram.
  • The VIEW: see the photo, set the status, mark and export orders.
  • The Dashboard imports that file as today, with no change.
  • Fact: imports the set, registers each sale in test mode, saves the XML, builds the PDF and emails it.
  • Basics: staff login, private storage for photos, no secrets in public code.
Not in the MVP
  • The optional rejection explainer (A2).
  • Special cases: partial payments, payments made by someone else, wrong currency, refunds.
  • More channels beyond WhatsApp (and Telegram as a fallback), rate tiers and coupons.

Day 1 · Agree and start

Day 4 · Test and demo

  • Run sample orders from start to end
  • Fix, then prepare the demo

Needed before Day 1

  • A sample import and export file from the Dashboard. Its format is the contract for the VIEW and for Fact, because the Dashboard cannot be changed.
  • Test access or API keys for KeyFácil and Omni, ideally returning the XML. If they have none, Fact produces the files these tools already accept: one manual upload per batch, but no retyping.
  • The accountant’s tax fields and what is billed.
  • A WhatsApp business account, or a test number to start with.
  • Who validates, who exports and imports.

8 · To confirm

Questions that block or shape the MVP

  1. What file format does the Dashboard import and export (type and columns)? A sample would settle it.
  2. Do KeyFácil and Omni offer an API and test access? Who at Brasper can request the keys? Do they return the signed XML (and, in Peru, the receipt confirmation)?
  3. Which document does Omni issue in Brazil (national NFS-e, municipal, or NF-e)? What exactly is billed, the commission or the full amount, and which document type applies on each route? (The accountant.)
  4. Who validates payments, who operates the VIEW, and who exports from the Dashboard and imports into Fact? Are they the same people? Who validates outside business hours (Mon–Fri 7–18, Sat 8–14, Sun 12–14)?
  5. Does Brasper already have an official WhatsApp Business account, and who can set it up? Does the client need a login in the Web App, or just a link?
  6. Are the 7 people and ~60 operations a day measured or estimated?
  7. Is the rates service the same one that failed on 10 Oct?
  8. Is the optional rejection explainer (A2) needed at all, once real rejections from the test mode are known?
